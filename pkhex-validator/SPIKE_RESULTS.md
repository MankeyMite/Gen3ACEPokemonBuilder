# Feasibility result

Measured on 2026-08-30 with .NET SDK 10.0.400, the .NET 10.0.11 browser-WASM
runtime, PKHeX.Core 26.8.26, and Chrome 152.0.7977.64 on Windows.

## Decision

**Pass.** Current PKHeX.Core successfully parsed, decrypted, and validated an
exact encrypted 80-byte Gen III stored Pokémon generated by this repository's
production `buildPokemonBytes` function in browser WebAssembly.

The test boundary performs no JavaScript decryption, padding, or conversion to
a 100-byte party structure. JavaScript copies the 80-byte `Uint8Array` and uses
Base64 only as a lossless JS/.NET interop transport. C# rejects any decoded
length other than 80 and passes a copy directly to `new PK3(memory)`.

## Browser fixture results

| Case | Environment | Expected result | Observed | Time |
| --- | --- | --- | --- | ---: |
| Project-built FireRed starter Bulbasaur | GBA cartridge | Legal | Legal | 686.1–734.5 ms |
| Same Bulbasaur | Switch FRLG | Legal | Legal | 2.0–2.2 ms |
| Project-built Bulbasaur with Psycho Boost | GBA cartridge | Illegal | Illegal | 4.0 ms |
| Legal buffer with checksum byte changed | GBA cartridge | Illegal | Illegal | 1.2–1.4 ms |
| FireRed-origin egg hatched at an Emerald location | GBA cartridge | Legal | Legal | 11.9–12.2 ms |
| Same cross-game-hatched egg | Switch FRLG | Illegal | Illegal | 7.8–8.1 ms |

The first analysis pays PKHeX's lazy static-data initialization cost. After that,
the median of the five measured checks was 4.0 ms.

PKHeX's `LegalityAnalysis.Valid` does not include the PK3 checksum in its
aggregate result. The bridge therefore also reads PKHeX's public
`PK3.ChecksumValid` result, adds a stable `Checksum` check DTO, and requires both
the legality analysis and checksum to pass for `valid: true`.

## Startup and payload

- Two cold isolated Chrome profiles, local loopback server, page start to
  exported validator ready: **307.5–346.9 ms**.
- Time inside `dotnet.create()` through exported assembly availability:
  **230.7–235.9 ms**.
- Browser resources transferred by the uncompressed local QA server:
  **42,712,758 bytes** (42.71 MB including HTTP overhead).
- Published uncompressed files: **42,695,546 bytes**.
- Published Brotli variants: **10,088,087 bytes**.
- Published Gzip variants: **14,047,490 bytes**.
- Full on-disk publish directory, containing all three variants:
  **66,831,123 bytes**.
- PKHeX.Core alone: **18,851,609 bytes uncompressed** or
  **3,014,972 bytes Brotli**.

The startup measurement is a local-loopback CPU/startup baseline, not an
internet cold-load estimate. A deployment that cannot serve the precompressed
files with the matching `Content-Encoding` will deliver the much larger
uncompressed payload.

## Scope retained for final integration

This spike does not modify the existing builder Generate flow, Legal Mode,
legality checker, or UI. It does not add a Web Worker. The intended production
follow-up remains a lazy singleton loader, a dedicated worker with FIFO request
processing, request IDs, and a separate PKHeX result/stale-state UI.
